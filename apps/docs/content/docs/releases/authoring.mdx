---
title: Release intent
description: Declare whether a merged pull request needs a tools release.
---

Every pull request adds one immutable file directly under
`.github/release-intents/`. Name it with a new lowercase UUID and use this
strict shape:

```json
{
  "schema": "project-space.release-intent/v1",
  "intent": "patch"
}
```

The pull request does not choose a concrete version. After merge, one serial
queue reads intents in main-branch order, derives the next version from the
latest published signed release, reserves the exact Git tag, and starts the
existing signed publication pipeline. Concurrent pull requests therefore
cannot claim or collide on the same version.

## Authoring rules

- Use `none` when no new CLI, connector, installer, or machine-tool artifact is
  needed. The trusted gate rejects `none` for release-sensitive paths.
- Use `patch` for a compatible correction or small improvement.
- Use `minor` for a compatible new capability.
- Use `major` only for an intentionally incompatible release.
- Keep `package.json` version unchanged and never edit a historical file under
  `apps/docs/content/docs/releases/entries/`.

The queue publishes GitHub-generated release notes for the exact tag range.
Historical hand-authored release entries remain available in Project Docs but
are no longer part of pull-request authoring.
