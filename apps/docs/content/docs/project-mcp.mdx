Project Space exposes a Streamable HTTP MCP endpoint at:

```text
https://projects.os-home.net/mcp
```

Project Space provides the OAuth 2.1 authorization server itself. ChatGPT Work dynamically registers as a public client, uses PKCE `S256`, and receives rotating refresh tokens. There is no OAuth client secret to configure. Clerk only authenticates the user in the browser before Project Space shows the consent page. The same user and machine membership checks as the web application apply to every tool call.

## Connect ChatGPT Work

1. In ChatGPT Work, add a custom MCP server.
2. Enter `https://projects.os-home.net/mcp` as the server URL.
3. Sign in to Project Space and approve the requested read/write access.
4. Use `list_projects` and `list_machines` before selecting a repository or machine.

The server exposes these task tools:

- `list_tasks` lists open GitHub tasks in an authorized repository. Use `get_task` to read one task.
- `get_task_status` reads linked branches, pull requests, and workflow runs for a task.
- `create_task` creates a GitHub task. It requires a UUID `operationId`; reuse it only to safely retry the same draft.
- `update_task` changes a task title, body, labels, or open/closed state.
- `list_task_comments` reads comments and `add_task_comment` adds one. Comments are not idempotent; do not automatically retry an add after an unknown network result.
- `list_codex_tasks` lists Codex tasks already running on connector machines.
- `read_codex_task` reads a Codex task transcript.
- `start_codex_task` starts a Codex task from a GitHub task number and repository id, creating a Project-managed worktree. Set `dryRun: true` to validate the open task and target without starting Codex.
- `send_codex_message` sends, steers, or durably queues a message for an existing Codex task. Its Task Execution equivalent is `send_task_execution_message`.

Assignees are not exposed yet because the current Project Space GitHub backend does not support them. GitHub is the only task provider in this iteration. Azure DevOps is reserved for a later provider addition. Creating or changing a task, starting a task, or sending a message are marked as consequential tool calls so ChatGPT can request confirmation before invoking them.

## Send modes and results

Both message tools accept `mode: "auto" | "steer" | "queue"`; omitting it uses `auto`.

- `auto` uses the same authoritative state as the read tools. It returns `sent` for a verified idle session and `blocked` when a turn is active.
- `steer` targets one exact active turn. Pass the `expectedTurnId` returned by the latest read; it is required for this mode. If the active turn changes before delivery, the tool returns `blocked` with reason `turn_changed`.
- `queue` durably stores the message in first-in, first-out order when a turn is active, returns `queued` immediately, and dispatches it automatically when the session becomes idle. If the session is already idle, it can return `sent` immediately.

Supply one stable caller-generated `operationId` for every logical message, and reuse it only to retry that identical request. This makes retries idempotent instead of creating duplicate turns or queue entries.

Immediate sends and steering return `sent` or `steered` when accepted. With `wait: true`, they wait for the affected turn and return `completed`; `delivery` preserves the original `sent` or `steered` outcome. Approval or input requests produce `blocked`, while a delivery that cannot be safely reconciled produces `uncertain`. Queue acceptance behind active or earlier work returns `queued` immediately, including when `wait` is true. If no work is ahead and the task is idle, queue mode dispatches immediately and honors `wait` like a normal send.

Task Execution responses also include `messageOutcome`. It preserves the message result and any blocked reason even when the surrounding execution remains `running`, including on an idempotent replay.

The new modes do not broaden access. The legacy tool keeps its exact Environment, connector, and physical-machine selectors, and the Task Execution tool remains bound to its existing execution. Project Space applies the same user membership, machine ownership, connector-generation, and `project-space:write` checks before any message is sent or queued.

## Connect Codex

Register the same production endpoint from a terminal:

```sh
codex mcp add project-space --url https://projects.os-home.net/mcp
```

Codex opens Project Space in the browser for approval, then returns to the local app through a loopback callback. The MCP server remains remote and continues to use the production Project Space backend.

## Authentication configuration

No Clerk OAuth Application, Client ID Metadata Document (CIMD), Clerk Dynamic Client Registration, or client secret is needed. Project Space owns the OAuth endpoints and stores only hashed authorization codes and tokens in its database. Access tokens expire after one hour and refresh tokens rotate whenever they are used.

The deployed backend still consumes `CLERK_PUBLISHABLE_KEY` and `CLERK_SECRET_KEY` for the existing Project Space browser login. Set `PROJECT_SPACE_PUBLIC_ORIGIN` to the public HTTPS origin when it cannot be derived from the reverse-proxy headers. The MCP OAuth server publishes:

- `/.well-known/oauth-protected-resource/mcp`
- `/.well-known/oauth-authorization-server`
- `/authorize`
- `/token`
- `/register`
- `/revoke`
- `/mcp`

The read-only tools require `project-space:read`. Starting a task or sending a message additionally requires `project-space:write`. If `PROJECT_SPACE_ALLOWED_EMAILS` is configured, MCP users must remain present in that allowlist for token refresh and access.

Do not expose a Preview deployment as a trusted MCP server. Preview containers intentionally do not receive the Clerk secret or production database access.
