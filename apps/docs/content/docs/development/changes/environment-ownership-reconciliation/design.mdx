title: Design
description: Owner-preserving boundaries for Environment definition reconciliation.
---

## Context

The inventory query intentionally reads a user scope and an explicit deployment scope
together. The previous reconciliation pass removed `owner_user_id` before aliasing, so a
deployment built-in and a user-defined definition with the same UUID were indistinguishable.

## Goals and non-goals

Goals:

- Preserve owner provenance through the in-memory reconciliation boundary.
- Canonicalize equivalent built-ins without touching user-defined evidence.
- Keep public snapshots, duplicate violations, and authorization boundaries unchanged.
- Preserve configured Codex Host selection as an evidence-based boundary.

Non-goals:

- Broad repair or deletion of persisted rows; only the explicit, eligible ownership backfill
  below is allowed.
- Making a conflicted user catalog silently valid.

## Architecture

Database rows retain `owner_user_id` in typed intermediate records. The shared reconciler
builds built-in aliases from the visible catalog, keys each alias by owner and definition ID,
then strips the temporary owner field before returning the existing public snapshot.

The persisted ownership reconciler is a separate, repeatable boundary. It runs inside the same
transaction as fresh deployment projection writes, connector identity writes, and physical Host
membership writes. A shared transaction-scoped advisory lock serializes those evidence changes
with the candidate query and copy, so a concurrent update cannot leave a candidate permanently
unseen or create conflicting copies.

## Decisions

1. Keep owner scope on database-derived definitions and Environment records until reconciliation
   and validation finish.
2. Continue canonicalizing equivalent built-ins across the explicitly visible scopes, but key
   aliases by owner and definition ID.
3. Filter and remap only the built-in alias entry in its owner scope; user-defined rows are
   never removed or remapped by a built-in alias.
4. Strip the temporary owner field before returning the existing public inventory shape.
5. Keep the persisted migration, Tailscale projection, and downstream target projections
   owner-scoped; duplicate ambiguity remains fail-closed.
6. Keep migration `0059_tailscale_environment_ownership` as immutable historical startup
   behavior. It only copies when a current, online,
   deployment-owned Tailscale Environment has one OS/name match to one user-owned connector
   identity grouped into one local physical Host and the account has an equivalent built-in
   definition across slug, name, kind, operating-system family, supported architectures,
   bootstrap strategy, and ownership. Two connectors remain ambiguous even when they point to
   the same Host. The migration copies the Environment into that account with the same UUID and
   manual/user evidence, while leaving the deployment projection unchanged.
7. Suppress only a projection owned by `project-space:tailscale-deployment`, and only when the
   same-UUID user record is an equivalent built-in with resolved identity, manual user evidence,
   a Host ID, and the same copied kind, name, and resource mode. Unresolved, unrelated,
   user-defined, and projected records from any other owner cannot hide evidence.
8. Re-run the ownership copy after each fresh deployment projection and after connector identity
   or physical Host membership mutations. The reconciler evaluates candidates globally, retains
   connector identity in uniqueness, and updates an existing built-in copy only when its durable
   signature differs.

## Validation model

For canonical built-in `a`, deployment built-in `x`, and user-defined `x`, reconciliation
returns built-in `a`, user-defined `x`, maps only the deployment reference to `a`, and retains
the user reference to `x`. The duplicate user slug remains a reported inventory violation.

The configured runtime only projects a physical Host when the Environment has verified or
manual evidence resolving to exactly one Host. The supported start and send path retains that
same selected Host and Environment; unresolved, deployment-only, duplicate same-UUID, and
missing evidence remain unavailable through the configured service.

Integration coverage starts with representative owner-scoped database query rows. A real
`ProjectSpaceDatabaseRepository` reconciles the combined collision rows, then the configured
runtime constructs its own strict user-scoped repository over the same persisted fixture before
the HTTP start/send boundary. No preconstructed inventory snapshot bypasses either path.

## Risks and mitigations

- **Alias leakage into user records:** owner-scoped keys and built-in-only filtering prevent
  cross-owner remapping or removal.
- **Public contract drift:** intermediate ownership fields are stripped before validation and
  return.
- **Hidden ambiguity:** existing duplicate violations remain visible and fail-closed.
- **Fabricated target:** configured runtime projection requires exact owner-valid Host evidence;
  otherwise the service returns the existing actionable unavailable result before dispatch.
- **Unsafe backfill:** the historical migration and repeatable reconciler insert no row when the observation matches multiple
  accounts, connector identities, or Hosts, including multiple connectors grouped into one Host,
  when the evidence is stale/offline, or when the account has a user-defined definition at that
  identity. A built-in with any incompatible blueprint field is also ineligible. Existing rows
  with user-defined evidence are not overwritten.
- **Premature projection suppression:** combined presentation requires the complete repaired-copy
  signature and the exact deployment owner. A same-ID unresolved, unrelated, or user-defined
  account row, and every projection from another owner, remains visible.

## Migration and rollout

The forward migration remains additive and historical. The runtime reconciler repeats the exact
eligibility check after fresh projection and membership mutations; ambiguous or stale evidence is
left untouched, and the original deployment projection remains intact. Combined presentation
hides only the matching deployment projection after a fully repaired built-in account copy exists,
preserving unresolved, user-defined, and unrelated evidence.

## Validation

- Focused model and repository regressions cover the canonical `a`, deployment `x`, and
  user-defined `x` collision, including equal built-in UUIDs across owners.
- The configured repository/HTTP regression captures repository reconciliation, HTTP start and
  send, and proves deployment-only, duplicate same-UUID, missing, and conflicting Host evidence
  fail closed before dispatch.
- Type checking, the full Bun test suite, and the project/prototype build pass locally.
- The exact pull-request head is checked by the repository preflight before push.
- Migration SQL and lifecycle coverage prove the exact eligibility, repeatable owner-scoped copy,
  unchanged deployment projection, atomic evidence boundary, and ambiguity no-op behavior.
