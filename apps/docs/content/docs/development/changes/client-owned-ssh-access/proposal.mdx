## Summary

Expose a typed, project-scoped SSH launch description from Compute and let the local Project
CLI perform the connection. The server authorizes and describes a fresh Tailscale target; the
client owns Tailscale reachability, host-key verification, credentials, the SSH process, and all
terminal traffic.

## Problem

The existing Compute presentation can describe SSH evidence but does not provide a safe,
client-owned launch boundary. A server-side relay would expose credentials and terminal traffic
to Project Space and would make stale or ambiguous target evidence unsafe.

## Scope

- Project fresh Tailscale SSH metadata with the exact `100.x` target address, port, user, verified
  host-key fingerprint, and opaque target identity revision.
- Add `project ssh [environment-instance]` and display the exact informational UI command using
  `--environment-id`; the browser does not launch a session until a trusted local bridge exists
  (#831).
- Require local Tailscale readiness, direct IPv4 use, a live target host-key probe, and strict
  temporary known-hosts verification before starting local interactive SSH.
- Return distinct local-client, Tailscale, target, SSH, host-key, authentication, and Codex
  failure states for the shared browser/runtime boundary.
- Preserve project-scoped live access semantics and honest stale, unavailable, and policy-blocked
  states.

## Out of scope

- Running SSH, terminal, credentials, agent sockets, or remote commands on the Project Space
  server.
- Treating MagicDNS, ordinary DNS aliases, or server-side connectivity as a readiness proof.
- Provider-native Codespaces access or a connector fallback.
- Providing a browser-to-local Project CLI bridge; this remains tracked in #831.
